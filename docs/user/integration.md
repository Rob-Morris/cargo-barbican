# Integration

How a consumer repo adopts cargo-barbican.

> The core Rust reviewed-target flow now exists end-to-end. Some consumer
> template files are still planned and are called out below where relevant.

## Consumer flow

1. Install:

   ```bash
   cargo install --locked --git https://github.com/rob-morris/cargo-barbican --tag v0.6.0
   ```

2. Copy templates into the consumer repo:

   ```bash
   # From the cargo-barbican repo root:
   cp -r templates/dependency-reviews /path/to/consumer/docs/
   cp templates/reviewed-targets.toml /path/to/consumer/
   ```

   Today the review-record template and reviewed-target manifest are shaped.
   The `deny.toml` and `dependency-management.md` templates remain planned, so
   keep using the consumer repo's existing equivalents until those templates
   ship.

3. Write the first inherited review records:
   - `cargo-barbican` itself, as the tool install
   - `cargo-audit` and `cargo-deny`, as prerequisite tooling

4. Run the smoke checks:

   ```bash
   cargo barbican pin-check
   cargo barbican audit
   cargo barbican verify
   ```

   `verify` now reuses the default `pin-check` gate before locked build/test
   execution, so the separate `pin-check` run is mainly for seeing the reviewed
   target report directly before the build step. The reviewed-target gate also
   expects each active family to point at a real checked-in review record. For
   crates.io reviewed families, prefer the structured `resolved` form in
   `reviewed-targets.toml` so `pin-check` can verify both the reviewed version
   and the reviewed tarball `checksum_sha256` against `Cargo.lock`.

5. Update the consumer repo's `AGENTS.md` so dependency-gate instructions
   point at `cargo barbican` instead of a manual process.

## Versioning and re-sync

Consumers pin a specific tag. Template files should include a header comment:

```text
# Synced from cargo-barbican v0.6.0
# Edit upstream and re-sync; do not edit this file directly.
```

When cargo-barbican releases a new version, the consumer:

1. Re-runs the copy step from the new tag.
2. Reviews the diff.
3. Updates the tool-install review record to cite the new version.

There is no automatic sync mechanism in v0.1. Re-sync is deliberate and
reviewed.
