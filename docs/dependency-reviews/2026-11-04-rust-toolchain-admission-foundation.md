# Rust toolchain admission identities and source evidence

This implementation uses the already reviewed graph. It adds no dependency, installer, cryptographic implementation or source-code execution. `crates/barbican/src/toolchain_admission/` owns pure identity reconstruction, strict records and eligibility. Authentication, bounded acquisition, local authority, filesystem containment and current installed inspection remain effects-adapter responsibilities. Parsing a record never establishes any of those facts.

## Identities and scopes

`Subject::reconstruct` reselects the exact closure from the original manifest and requires every corresponding archive inventory. It combines payload expectations through the existing collision checker and commits the payload plus package metadata, including the component installer manifest. The three bounded installer text bodies must match their metadata hashes and lengths. A stored `SubjectRecord` must equal this reconstructed subject; a supplied bare mapping digest is not accepted as source proof.

Identity protocol version 1 hashes an eight-byte big-endian domain length, the domain bytes, then complete UTF-8 JSON. Each protocol record has fixed field order; unordered sets/maps and archive/source lists are sorted before hashing. Mapping serialization streams into the existing SHA256 implementation. Changes to this protocol require a versioned identity/mapping change. Archive modes remain exact source facts. Only the independently qualified native adapter applies observed installer transformations.

Evidence content identities include source identity, provenance, revision, content digest, portable snapshot reference, coverage and actual expiry. They exclude successful observation check times. Refreshing unchanged evidence therefore does not rewrite an assessment or personal acceptance time. Findings preserve change and exposure as independent axes; source-lock inclusion is not a claim of shipment or reachable exposure.

Personal acceptance and repository governance are separate. `[[rust.toolchains]]` binds subject, policy, repository assessment, scope, completed prose and portable evidence paths/digests. It does **not** bind another person's local acceptance event. A new user must explicitly establish their own local acceptance. Copying portable evidence cannot establish that event or a continuing-use binding.

The current repository's optional `[toolchain].admission_scope` supplies its deliberate governance scope; an admission record cannot nominate its own authority. It is a stable operator-chosen repository label, not an inferred Git remote or private absolute path. `[toolchain].require_admission` defaults to false for legacy configurations. Repository toolchains remain separate from crate families and cannot satisfy the active-family floor. Integration must enforce the opt-in before invoking Cargo or candidate probes.

Review deadlines are optional. A chosen `review_by` is inclusive of that UTC date. Exact subject/policy/repository-scope age exceptions require completed prose and a finite UTC expiry; they waive age only. Crate-family grants do not transfer.

## Eligibility contract

New personal/repository admission, installation, first adoption and changed consumer/policy/scope require fresh mutable evidence. Online mode requires successful source checks during the current operation. Explicit cached mode is supplied only for that operation, requires a reason, and is bounded by 24 hours from the oldest required source check and any earlier real expiry. Reading, hashing, copying or accepting stored bytes does not renew source check times.

Continuing local use and activation receive the exemption only when the same subject, portable admission identity, actual local consumer identity and currently inspected installation match a durable local binding. They do not expire solely because evidence is 48 hours old. They still enforce current policy, chosen deadlines, actual expiry, current source snapshot hashes, retained adverse knowledge, observation rollback refusal and current installed correspondence. The caller must derive the local consumer identity independently from the actual context.

The source floor is explicit: distribution authentication, publication, release notes and security announcements; and source identity plus advisories for every selected package/target. Missing, failed or inapplicable collection cannot become residual uncertainty. Unknown coverage must be represented and explicitly assessed. Advisory coverage cannot claim established applicability while component source identity is unresolved. Every required source snapshot is checked against its portable reference and SHA256.

Publication maturity uses the end of the latest corroborated UTC day for these exact subject bytes. Missing, inconsistent or future required facts refuse. The tiny whole-second minimum-days threshold is shared with the existing crate release-age owner; crate yanks, source facts and exception precedence remain unchanged.

## Source collector qualification

The S6 source research and report were reread before implementing the narrow RustSec archive reader. In particular, compiler/tools, std, Cargo and LLVM are separate source corpora; Cargo's advertised Git commit can identify the Rust tree rather than the Cargo submodule.

The reader accepts a single fully consumed gzip stream, at most 8 MiB compressed, 64 MiB expanded, 20,000 physical tar headers, 4,096-byte paths and 2 MiB per member. It does not extract files. It accepts only ordinary files/directories plus one initial, at-most-128-byte Git global PAX record whose entire body is the exact expected commit comment. Per-entry PAX, GNU extensions, links, special members, duplicate/unsafe paths, changed roots, trailing payloads and unsupported schema refuse. Required RustSec frontmatter is closed and preserves withdrawn/informational/affected-platform/function information.

The existing current RustSec database at revision `965bf9ad083b58e6340d65829d85217b18be9290` was archived with trusted Git as inert data. The product reader parsed all 1,406 advisory documents (1,386 crates.io and 20 Rust corpus records), including the actual ctutils 0.4.2 affected / 0.4.4 patched controls. The archive was 547,662 bytes with SHA256 `bd6a40594d19f3eeb21764c25954f556344bc492eea99a7fb798e38a61ca5710`; this proves the exact retained Git snapshot route, not every future GitHub archive format.

At the initial checkpoint, source-range evaluation refused prerelease comparators, wildcards and package build metadata. That conservative restriction was not sufficient for the real candidate's source locks; the representative qualification below supersedes it. [RustSec version evaluation](https://github.com/RustSec/rustsec/blob/bec1cd21fcfdd2a102109273914587bb2d51914e/rustsec/src/advisory/versions.rs) routes through OSV ranges; this module does not claim to implement all RustSec semantics. Unsupported required evaluation is a blocking gap, never a clean result. Withdrawn records remain distinguishable and future/inconsistent advisory or withdrawal dates refuse.

The current Rust corpus contains std (18), rustdoc (1) and Cargo (1). The retained `rust/cargo/CVE-2019-16760.md` explicitly uses Rust distribution numbering (`>= 1.26.0`), whereas the Cargo security GHSAs identified by S6 use Cargo package numbering (`< 0.97.0`). A corpus/package label alone must not erase that distinction. Source inclusion, native vulnerability coverage and selected-host binary correspondence remain separate from range evidence.

## Qualification limits

### Representative stable-source range follow-up

The first 1,406-document test established parsing, not applicability matching against candidate package versions. A later production review exposed rkyv 0.8.18 against prerelease bounds in RUSTSEC-2026-0233/0234/0235. The actual source locks also contain build metadata, including libgit2-sys 0.18.2+1.9.1. Refusing those cases made the representative review unusable.

The correction is narrow. Stable target versions can use the existing semver matcher against prerelease bounds because Cargo's prerelease opt-in rule only affects prerelease **targets**. Comparison ignores build metadata while records retain the full original version. RustSec's [OSV selector conversion](https://github.com/RustSec/rustsec/blob/bec1cd21fcfdd2a102109273914587bb2d51914e/rustsec/src/osv/unaffected_range.rs) zero-fills missing minor/patch numbers for relational/exact bounds; the adapter applies that precision rule before matching. Caret/tilde granularity is retained. Bare `*` has no comparators and represents an unbounded range; explicit wildcard operators remain unsupported by that RustSec conversion. Prerelease targets, malformed/unsupported bounds and impossible intervals still refuse. No dependency or general range engine was added.

The primary-source snapshot is bound to immutable RustSec commit `bec1cd21fcfdd2a102109273914587bb2d51914e` (its pinned bytes match the initially fetched source), with SHA256 `e020b8680a90bb37bdf225c8e7d6578a1646ae777f1cda257df1f2a9a546decd`. A data-only qualification exercised all 273 relevant advisory/version pairs across 1,093 registry-package occurrences in the actual 669-package Rust, 49-package std and 550-package Cargo source locks. The 30 affected source observations exactly matched preinstalled cargo-audit 0.22.1 using the same pinned database with `--no-fetch`: Rust 9, std 0, Cargo 21; no missing or extra observations. None of these locks has a prerelease registry target. Offline registry-index gaps affected the oracle's separate yank checks, so this is range parity, not a complete clean audit.

The [machine receipt](2026-11-04-rustsec-stable-range-qualification.json) records exact lockfile/source/oracle hashes and output receipts. The temporary qualification integration test was removed after preserving its non-executable source. Source inclusion still does not establish shipment, reachability, native vulnerability coverage or compiler safety.

Independent Sol review then identified a remaining malformed-input gap: RustSec rejects overlaps across the combined `patched` and `unaffected` lists, while the first adapter merely matched each list. The parser now rejects those overlaps before constructing an advisory, including overlaps within either list and intersections containing only prereleases. The private validation uses the closed source-selector bounds already qualified above, at most 128 ranges per list, with pairwise checks over the combined list. Inclusive/exclusive touches and caret/tilde upper bounds at the next family's `-0` prerelease follow [RustSec's combined-range validation](https://github.com/RustSec/rustsec/blob/bec1cd21fcfdd2a102109273914587bb2d51914e/rustsec/src/osv/ranges_for_advisory.rs). The existing scanner's `VersionInterval` was not reused because it models Cargo precision over stable triples and deliberately cannot represent these prerelease bounds. Stable matching still uses semver; no general range engine or scanner refactor was added.

After that correction, nine focused source tests passed, all 1,406 current records parsed, and all 273 representative queries again produced exactly the same 30 oracle findings, with zero missing or extra. The follow-up source and receipt are retained, and its temporary integration test was removed before the final gate.

Native installer metadata rules are owned and tested separately by the native workflow. The bounded archive-mode extension retains the exact regular-file modes 0400/0600/0700 in addition to 0644/0755; directories remain 0755 and privileged modes refuse. The S4-V report and pinned Rustup `28d1352dbcb436d3111c3594b9e1588e94950464` package source corroborate observed 0400→0444, 0600→0644 and 0700→0755 transformations. These facts do not qualify another evaluator, encoding or platform.

Tests exercise same-context 48-hour continuation versus fresh admission/install, cache boundaries, earlier expiry, new consumer and policy, original human approval time, independent CI acceptance, source and prose tampering, known adverse observations, rollback (including different source content/provenance observed in the same UTC second), publication precision, scoped exceptions, optional deadlines, strict schema/family separation, malformed archives and unsupported advisory interpretation. The full library suite passed 368 tests in 8.16 seconds; the subsequent source-identity rollback refinement passed all 27 focused admission/source tests in 0.45 seconds. The full retained RustSec qualification passed in 0.26 seconds. All used the reviewed graph, explicit trusted Rust 1.95.0 and `--locked --offline`. The temporary corpus qualification integration test and owned archive were removed; non-executable test source and receipt remain under the root's scratch directory. Full feature enablement still requires the coordinated effects path and the requested design/security reviews; this pure layer is not a standalone installation clearance.
