# v0.29.0 — 2026-10-14

**Summary** Add pinned process-isolated verification tests

Consumer repositories can select cargo-nextest through checked-in verification
policy while keeping the existing toolchain, reviewed-target and locked-build
gates. Repositories that use the default runner retain cargo-test.

- `[verify].test_runner` selects `cargo-test` or `nextest`; nextest requires a
  canonical exact stable `nextest_version` of at least `0.9.128`.
- `verify` and `gatehouse pre-release` validate policy before their gates.
  Nextest availability/version errors fail before tests, with no fallback or
  tool installation. The version check establishes compatibility, not provenance.
- The toolchain preflight rejects nextest-specific Cargo environment/config
  aliases that could replace the installed delegate; unrelated aliases remain
  ordinary inputs.
- Nextest runs with the default profile, default filters bypassed, zero
  retries, fail-fast and successful empty-suite handling.
- Cargo doctests include every default member to retain feature activation.
  No-enabled-library scopes skip doctests; mixed enabled/disabled library
  scopes fail closed because explicit Cargo `--doc` overrides `doctest=false`.
- `scripts/verify-nextest.sh` exercises actual Cargo/nextest subprocesses and
  failure/coverage fixtures on macOS and Linux CI, using reviewed
  `cargo-nextest 0.9.146` installed with `--locked --no-default-features`.
- Config parsing, metadata scope selection and CLI/Gatehouse behaviour have
  offline regression coverage. Product dependencies and default scaffolds keep
  their existing semantics.
